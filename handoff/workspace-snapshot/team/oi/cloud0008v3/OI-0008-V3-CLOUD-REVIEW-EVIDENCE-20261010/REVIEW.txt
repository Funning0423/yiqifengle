2. 当前v3独立端到端复现
见results/summary.json及各场景目录。输入是明确的fake CLI、本地模拟日志、Node VM console/wx，审计源文件完全不改。每个场景都核实close只传本次自己复制的projectDir，进程结束后原工具SHA清单仍有效。

已改善、通过相应防错检查：
- healthy：PASS/exit0，是mock阳性健康对照；绝非真实游戏首开通过。
- missing-root-error：运行中创建日志根、写本项目TypeError，FAIL/1。
- truncate-error：截断后的本项目TypeError，FAIL/1。
- unrelated-only：只有其他项目强错误/没有本项目日志canary，BLOCKED/2。
- cli-exit7、close-exit5：BLOCKED/2。
- cli-lingers-error：长驻自己的CLI输出TypeError，FAIL/1；cli-lingers-clean：只终止自己的未退出CLI并BLOCKED/2。
- no-logs：BLOCKED/2。
这些运行结束后的每组manifest均自洽；未重现v1的run.log在冻结后被追加问题。

阻断发现A：WeappLog/CLI的错误识别比规则文件更窄（audit:35–46、389–396）。
实际审计只在STRONG_ERROR_PATTERNS命中后调用add。该表遗漏通用“Error: ”、任意“[其他错误]”，也不读取日志里的console.error级别。结果：
- weapp-generic-error：本项目WeappLog “[console.error] Error: ordinary runtime failure” -> PASS/0。
- weapp-unclassified-error：本项目 “[console.error] plain fatal diagnostic” -> PASS/0。
- weapp-unattributed-generic：OTHER-PROJECT普通Error -> PASS/0，甚至不进入unattributed，违背“无归属error一律BLOCKED”。
- weapp-bracket-error：“[其他错误] 资源加载失败” -> PASS/0。
- cli-generic-error：自己的CLI stderr “Error: ordinary launch failure”，code0 -> PASS/0。
三路canary全部满足也不能补上分类器遗漏。独立boundary测试同时证明前两类在first_open_console_rules.classifyText中是forbidden，但auditStrongPatternHit=false。
应统一规范化/级别识别/错误规则，未能理解的error至少BLOCKED，不应被当普通信息丢弃。不要只补当前几个字面串后宣称涵盖所有错误。

阻断发现B：canary不是精确消息匹配，会整条隐藏附带真实错误（audit:48、362–383、392）。
CANARY_RE无行首/行末限定。只要一条消息含“[QF-AUDIT-CANARY(-LATE)] <本次token>”，整个消息立即continue，后面的真实TypeError不再分类。
- canary-mixed-error：WeappLog同一行canary后跟TypeError -> PASS/0。
- canary-mixed-console：console.error同一消息canary后跟TypeError，同时进入automator/shim/日志 -> PASS/0。
这是单条记录拼接/格式边界的确定性反例，不是证明真实DevTools一定会拼接。应只豁免规范化后的精确canary事件，保留其他payload/同一行其他错误。任何包含额外文本的canary样式记录不能整条免检。

阻断发现C：声称boot canary已捕获，实际上LATE也能冒充（audit:383、411、429）。
canarySeen.shim用同一允许-LATE的正则，之后直接存成channels.shim.canaryAtBoot。读取到的R.shim.canaryAtBoot标志不参与判定。
- canary-boot-missing：模拟读取的shim errors只剩LATE，canaryAtBoot=false，仍PASS/0且channels称canaryAtBoot=true。
因此当前不具备自称的启动阶段证明。应分别验证精确boot/late记录、当前token和安装能力，缺失就BLOCKED，不能只改字段名称仍宣称覆盖首开。

阻断发现D：允许名单可以吞同一日志行前部的真实错误（audit:369；rules:extractKnownNotice）。
末尾抽出熟悉的app.json句子后，整条日志被分为knownNotice；未先保留前部其他错误。独立mixed-error-notice-allowlisted场景在同一行先放“TypeError: actual failure;”，后放精确通知，仍得到PASS_WITH_ALLOWLISTED_IDE_NOTICE/3，而不是FAIL。
纯精确通知默认FAIL；启用允许名单后只给特殊状态/exit3，未观察到普通PASS。这一上限确实保留，但“0 other errors”的声明仍不成立。应逐记录剥离可信日志前缀，并先判其他真实错误，不能用任意末尾匹配免掉整行。

边界发现E：tailer没有检测同前缀的后段原位改写（audit:204–212）。
本地文件4297字节：baseline后保持inode/大小/前4096字节不变，只把其后内容换成TypeError，再poll/stop。得到lines=[]、incomplete=[]。原位改写检测只是首4KiB指纹，不能保证所有改写均被发现。该本地反例没有证实真实WeappLog写入协议会这样改写；应明确只支持什么日志协议，或扩展一致性判断，不作“任意可能缺口均阻断”的无条件承诺。
