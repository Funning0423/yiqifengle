五、测试保障的剩余缺口
1. 源码 pin 默认变弱。O/replay.cjs:4 无条件核对 v3 audit 完整 SHA；新 replay.cjs:5 仅在 REVIEW_EXPECT_SHA 非空时核对。:26 只记录实际 SHA，不能替代预先拒绝错版本。本次 v4 audit SHA 为 d466c6413f75fd7224ee4858ea3fca23509585de0f7382a63a09c108e9485ae2。独立运行应显式设置此 SHA，并保持外层/整包清单校验；README:93 已如实披露可选 pin。
2. exit 没进入 ok。新 replay.cjs:23 只检查 status 与 manifest；:24 仅把 r.status 写进结果。旧 O/replay.cjs:21–22 同样如此。若将来 status 为特殊放行却 exit0，22/22 可能仍显示成功。应独立核对或补 expectedExit 映射，且核查 spawn error/signal/timeout。不能把这个原有覆盖缺口说成 v4 偷改测试。
3. 场景断言通常只到最终状态；比如 canary-boot-missing 的 BLOCKED 不要求 missing 中恰好是 boot 证据缺失，而不是其它碰巧阻断。父任务运行应读原因和 channels。close-target 两个 every 在空动作列表时也可能真，这同属旧限制；可在独立结果核实动作存在与具体目标。
4. 新规则测试仍未覆盖“错误前缀 + 行内级别标签”的混合记录，且源码有明显静态风险：rules.parseLogLine:65–66 取任意位置首个 [log]/[error] 等级别标签，将其前全部内容放 prefix；audit:413 虽保存 prefix，但 :419 只传 payload 分类。因此“本项目 TypeError: real failure [log] harmless”会把前段真实错误丢在不分类的 prefix；“TypeError: ... [error] <精确通知或 canary>”也可能重新形成整段免检。test_rules_v4.cjs:19–29 的混合用例没有这一切口，不能靠现有 22 场景排除。此处是静态推断，已交父任务运行分工验证；未在本分工运行任何样例。
