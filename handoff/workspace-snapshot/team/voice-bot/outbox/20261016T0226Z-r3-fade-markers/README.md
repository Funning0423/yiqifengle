说明：
- 14dB 是 summary.md 用其他窗长量的数值；这里按 20ms 窗、10ms 步长测，80ms 内跌 8.4dB，150ms 内的跌幅更大。时间点一致（视频 28.64–28.74s）。
- 混音里 BGM 一直在，电平比音效高，所以 RMS 里还有其他 ≥6dB 的跌落，但都是 BGM 起伏（见 markers.json 的 drops_ge6db 列表，参考包络同段没有变化）。音效窗口里只有夜间 tf84 这一处不是 BGM。
- 风声循环：用 1s 片段做互相关，最大约 0.5–0.57，音效开始之前的背景段也差不多，区分不出来。而且录音在 sailGone 就停了，落地后的风声没录到。
- 跳过录屏（第 13 项）也有同样的 1.8s 超前：音效起点 25.74/25.76s，sailStart 27.55s。点击 30.18s 后的掉落和点击时刻对得上，说明音画混流基本没错位，超前是游戏里真实发生的。

## 结论
按音效自己的时钟算，夜间的淡出在 tf84 左右开始（音效 +2.80s，80ms 内落下），只比 tf81 sceneSwap 晚约 3 帧，和设计里“草甸还没准备好就停在云里”的 80ms 淡出吻合。白天草甸按时准备好，所以没有触发，音效自然播完。真正的问题不是淡出触发得太早，而是**音效（以及驱动淡出的计时）比画面上的启航早了约 1.78s（≈53 个 timing 帧）**。按画面时钟算，淡出落在 sailStart +1.02s（≈tf31），船还在海上，整屏云要到 30.0s 才出现。建议 @运镜bot 查音效 play() 和“等待草甸”计时是从什么事件开始的，为什么比帆船节点激活和画面早 1.8s；也查一下夜间画面为什么比时序模型慢。
